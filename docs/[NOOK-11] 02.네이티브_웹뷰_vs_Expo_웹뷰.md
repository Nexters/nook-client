# 네이티브 웹뷰 셸 vs Expo 웹뷰 셸

| 작성자 | 작성일 | 수정일 |
| --- | --- | --- |

> **이 문서는 의사결정 기록(ADR)이다.** 2026-07 시점에 두 방식을 다 만들어 보고 비교한 내용이며, **결론은 Expo 셸 채택**이다.
> 아래 본문의 공유(App Group·공유 확장·`NookShare` 모듈) 관련 서술은 **비교 당시의 기록**이다. 현재 코드에는 공유가 없다(별도 PR 로 분리). 현재 구현 상태는 `docs/native-bridge.md` 를 본다.

## 한 줄 요약

둘 다 "얇은 셸이 원격 웹을 띄우고 공유만 네이티브로 받는" 같은 구조다. 다른 건 **셸을 무엇으로 짜느냐**뿐이다 — Swift/Kotlin 2벌이냐, TypeScript 1벌이냐.

## 두 구조

**네이티브 셸** (`feat/migrate-native-shell-webview`)
```
[iOS] WKWebView + Swift 셸  ┐
                            ├→ 원격 웹(app.nook.com)
[And] WebView  + Kotlin 셸  ┘
```

**Expo 셸** (`feat/migrate-expo-shell-webview`, 채택)
```
[iOS/And] Expo(RN) App.tsx + react-native-webview → 원격 웹(app.nook.com)
                  └ NookShare 네이티브 모듈(Swift) → App Group 읽기   ← 비교 당시. 현재는 제외
```

웹(`apps/web/`), 계약(`packages/bridge-contracts`), 공유 확장(SwiftUI/Kotlin) 은 **양쪽이 동일**했다. 재작성한 건 셸뿐이다.

## 핵심 차이

| 항목 | 네이티브 셸 | Expo 셸 |
| --- | --- | --- |
| 셸 코드베이스 | iOS·Android 2벌 | 1벌 (`App.tsx`) |
| 언어 | Swift + Kotlin | TypeScript |
| 웹→네이티브 API | 플랫폼마다 다름<br>(`webkit.messageHandlers` / `NookNative`) | 통일<br>(`ReactNativeWebView.postMessage`) |
| App Group 읽기 | 셸에서 바로 | **네이티브 모듈 별도 작성** |
| 런타임 | 웹뷰만 | JS 런타임(Hermes) + 웹뷰 |
| 네이티브 프로젝트 | 직접 소유, git 추적 | prebuild 생성물, gitignore |
| 공유 확장 유지 | 프로젝트에 그대로 존재 | prebuild 가 덮어씀 → config plugin 필요 |
| 툴체인 | Xcode/Gradle 표준 | **Expo SDK ↔ Xcode 버전 결합** |
| OTA 업데이트 | 불가 | EAS Update 가능 |

## 실제로 겪은 차이

문서용 추측이 아니라 이번에 양쪽을 다 만들면서 나온 것들이다.

| 겪은 일 | 어느 쪽 | 결과 |
| --- | --- | --- |
| Xcode 26.2 에서 Expo SDK 57 자체 Swift 코드가 컴파일 실패 | Expo | Xcode 26.6 으로 올려서 해결. SDK 가 툴체인 버전을 강제함 |
| App Group `pending` 읽기 | Expo | JS 라 직접 불가 → `NookShare` 모듈 신규 작성 |
| 같은 App Group 읽기 | 네이티브 | 셸 코드에서 바로 됨, 추가 작업 없음 |
| 공유 확장 주입 | Expo | `apps/mobile/ios` 가 생성물이라 수동 주입, `prebuild --clean` 시 소실 |
| Vite dev 서버 리로드로 공유 유실 | **양쪽 동일** | 셸 문제가 아니라 웹뷰+dev 서버 공통 함정 |

## 장단점

**Expo 셸**
- 👍 셸 로직 1벌 — 브리지·공유 전달 로직을 두 번 안 짬
- 👍 TypeScript — 웹 프론트 중심 팀 역량과 일치
- 👍 EAS Update 로 셸/웹 로직 OTA 배포 가능
- 👎 네이티브 접근마다 모듈 작성 비용 (App Group 이 첫 사례)
- 👎 prebuild 재생성 관리 필요 (config plugin 없으면 수동 작업이 계속 날아감)
- 👎 Expo SDK 가 Xcode 버전을 강제 — 팀 전원 툴체인을 맞춰야 함
- 👎 JS 런타임만큼 앱 용량·초기 구동 비용 증가

**네이티브 셸**
- 👍 네이티브 API 직접 접근 — 중간 계층 없음
- 👍 의존성 최소, 앱 가벼움
- 👍 툴체인 자유 (Xcode 버전 강제 없음)
- 👍 공유 확장이 프로젝트에 그대로 있음 — 생성물 관리 이슈 없음
- 👎 셸 로직 2벌 유지 (iOS/Android 각각)
- 👎 Swift/Kotlin 필요 — 현재 팀의 약한 부분
- 👎 브리지 계약 변경 시 양쪽 수정

## 판단 기준

셸이 계속 얇게 유지되느냐가 갈림길이다.

- **셸이 계속 얇으면** → 네이티브 2벌이어도 코드가 몇백 줄이라 중복 비용이 작다. 반대로 Expo 의 "1벌" 이점도 작아지고, 툴체인 결합·prebuild 관리 비용만 남는다.
- **셸이 두꺼워지면**(푸시, 위치, 딥링크, 백그라운드 동기화 등) → 2벌 유지 비용이 빠르게 커지고, TypeScript 로 한 벌만 짜는 Expo 가 유리해진다. 단 기능마다 네이티브 모듈이 필요할 수 있다는 건 감안해야 한다.
- **네이티브 저장소 접근이 많을수록** Expo 의 모듈 작성 비용이 누적된다. 이번 App Group 건이 그 첫 샘플이다.

비교 시점의 셸은 (웹뷰 + 브리지 + 공유 전달) 수준으로 매우 얇았다. 두 방식의 실질 차이가 작았기에, **앞으로 셸에 네이티브 기능을 얼마나 넣을 계획인지**가 결정 요인이었다 — 공유 수신에 이어 푸시·딥링크가 예정돼 있어 TypeScript 한 벌로 가는 Expo 를 택했다.
